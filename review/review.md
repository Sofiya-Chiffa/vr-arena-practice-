### Замечание №1 (критическое). README описывает сценарий `close`, который нельзя воспроизвести

- **Файл:** `src/java/README.md`, раздел «Запуск», пример `close B0001 E0001`
- **Место в коде:** `src/java/src/ConsoleApp.java:16-22` (конструктор `ConsoleApp` инициализирует `InMemoryStorage` и заполняет demo-данными в `seedDemoData()` при каждом запуске)
- **В чём проблема.** README предписывает сначала запустить `java -cp out ConsoleApp book` (создаётся бронь `B0001`), а затем в отдельной команде `java -cp out ConsoleApp close B0001 E0001`. Но `ConsoleApp` хранит все данные в `InMemoryStorage`, который живёт только в рамках одного процесса. Каждый новый запуск `java -cp out ConsoleApp ...` создаёт пустое хранилище и заново вызывает `seedDemoData()`, где список брони `storage.getBookings()` остаётся пустым. Поэтому команда `close B0001 E0001` **всегда выводит «Бронь не найдена»** вместо обещанного README «Сеанс проведён, услуга оказана». Я проверила это посредством команд, указанных в README:
  ```
  $ java -cp out ConsoleApp book
  Бронь создана
   Бронь B0001 (клиент C0001, слот SL0003, статус ACTIVE)
  $ java -cp out ConsoleApp close B0001 E0001
  Бронь не найдена
  ```
  Получается, что основной пользовательский сценарий из README («закрыть бронь и создать сеанс») невоспроизводим. Демо-класс `Main.java` работает корректно (там всё в одном процессе), но в README в том числе описаны последовательные консольные команды, которые не выдают соответствующий результат.
- **Что предлагаю.** Либо явно описать в README, что команды `book` и `close` можно прогнать только вместе (например, добавить команду `demo`, которая за один запуск выполняет всю цепочку book-close), либо реализовать сохранение состояния между запусками - например, сериализацию `InMemoryStorage` в JSON-файл. Минимальный вариант - добавить в README честное предупреждение, что `close` работает только в рамках одного запуска, и привести пример команды `demo`.

### Замечание №2. `Validator.validateRequest` принимает `participants = 0` и отрицательные значения как корректные

- **Файл:** `src/java/src/util/Validator.java:10-58`, метод `validateRequest`
- **Место в коде:** проверки `scenarioId`, `slotId`, `phone` есть (строки 15-20), но проверки `participants` на неотрицательность нет, сравнение идёт только с максимумом в `scenario.canHost(participants)` (`model/Scenario.java:38-40` - `participants <= maxParticipants`).
- **В чём проблема.** Я запустила три контрольных случая:
  ```
  participants=0  - "Заявка корректна"
  participants=-5 - "Заявка корректна"
  participants=7  - "Ошибка: количество участников 7 превышает допустимый максимум 6"
  ```
  Нулевое и отрицательное количество участников пропускаются как валидные, хотя сеанс без участников не имеет смысла. Это логический пробел валидации.
- **Что предлагаю.** Добавить в начало `validateRequest` проверку:
  ```java
  if (participants <= 0)
      return "Ошибка: количество участников должно быть положительным";
  ```
  и поместить её рядом с проверками `scenarioId`/`slotId`/`phone` (строки 15-20).

### Замечание №3. В `InMemoryStorage` есть `clients` и `employees`, но demo-данные их не заполняют, а `BookingService` оперирует строковым `clientId` без связи с `Client`

- **Файл:** `src/java/src/util/InMemoryStorage.java:13-14, 48-62`; `src/java/src/util/BookingService.java:14-24`; `src/java/src/ConsoleApp.java:25-32` (`seedDemoData`)
- **Место в коде:** поля `clients`/`employees` объявлены и для них есть геттеры и `addClient`/`addEmployee`, но ни в `ConsoleApp.seedDemoData()`, ни в `Main.main()` ни один `Client` или `Employee` не создаётся. При этом `BookingService.bookSlot(...)` принимает `clientId` как строку и не проверяет, что клиент с таким ID существует.
- **В чём проблема.** Получается «висячая» функциональность: классы `Client` и `Employee` (и наследование `Person`) объявлены и есть на UML-диаграмме, но в работающей программе ни один объект этих типов не создаётся, и бизнес-инвариант «бронь может быть создана только для существующего клиента» нигде не проверяется. Можно создать бронь с `clientId = "C9999"`, которого нет в системе.
- **Что предлагаю.** Либо (а) добавить в `seedDemoData()` хотя бы одного клиента и одного сотрудника и проверять в `BookingService.bookSlot` существование `clientId` в `storage.getClients()` (бросать `IllegalArgumentException`, если не найден - это закроет пробел и сделает наследование `Person` осмысленным), либо (б) явно описать в README, что проверка клиента - на следующем этапе, а пока `clientId` - внешний идентификатор. Вариант (а) предпочтительнее: он связывает уже написанный код `Client`/`Employee` с работающей логикой.

### Замечание №4. В `Booking` и `Session` статус хранится по-разному - enum и строка

- **Файл:** `src/java/src/model/Booking.java:5` (`public enum Status {ACTIVE, CLOSED, CANCELLED}`) против `src/java/src/model/Session.java:10, 57` (`private String status; ... this.status = "COMPLETED";`)
- **Место в коде:** `Booking` использует типобезопасный enum для статуса, а `Session` - строковый литерал `"COMPLETED"`, который передаётся в конструктор как параметр `String status` и сравнивается/печатается как строка.
- **В чём проблема.** Несогласованность в одном пакете `model`: похожие сущности `Booking` и `Session` по-разному моделируют одно и то же понятие «статус». Строковый статус опасен опечаткой (например, `"Completed"` или `"completed"` уже не совпадёт) и не даёт автодополнения в IDE. Кроме того, `SessionService.closeBooking` принимает `String status` извне (`ConsoleApp.java:91` передаёт `"COMPLETED"`), что позволяет передать любое значение, в том числе невалидное.
- **Что предлагаю.** Ввести `Session.Status` enum по образцу `Booking.Status` (`PLANNED, COMPLETED, CANCELLED`), поле сделать `private Status status`, в `Session.complete(...)` присваивать `Status.COMPLETED`, а в `SessionService.closeBooking` - убрать строковый параметр `status` или принимать `Session.Status`.

### Замечание №5. `DateTimeUtil.parse` падает с `DateTimeParseException` на некорректной дате/времени, и это исключение нигде не обрабатывается

- **Файл:** `src/java/src/util/DateTimeUtil.java:18-20`; вызывается из `src/java/src/model/Slot.java:43-45` (`startDateTime`)
- **Место в коде:** `DateTimeUtil.parse(date, time)` вызывает `LocalDate.parse(date)` и `LocalTime.parse(time)` без `try-catch` и без проверки формата. `Slot.startDateTime()` прокидывает исключение дальше в `SlotService.findFreeSlots` и `Validator.validateRequest`.
- **В чём проблема.** Если в `Slot` попадёт дата не в формате `yyyy-MM-dd` или время не в `HH:mm`, программа упадёт с `DateTimeParseException` и стек-трейсом вместо понятного сообщения. В `Validator.validateRequest` проверяется `scenarioId`/`slotId`/`phone`, но формат даты/времени слота не проверяется. Это нарушает принцип единого подхода к ошибкам, который автор сама задала в `Validator` (возврат человекочитаемых строк «Ошибка: ...»).
- **Что предлагаю.** Либо валидировать формат даты/времени на этапе создания `Slot` (в конструкторе или в `Validator.validateRequest` перед вызовом `startDateTime`), либо обернуть `parse` в `try-catch` и возвращать `Optional<LocalDateTime>` / бросать собственное исключение с понятным сообщением. Минимальный вариант - в `Validator.validateRequest` добавить проверку формата через `try { DateTimeUtil.parse(...) } catch (DateTimeParseException e) { return "Ошибка: некорректный формат даты/времени у слота"; }`.

### Замечание №6. Дублирующаяся логика генерации ID в `BookingService` и `SessionService` с риском коллизий

- **Файл:** `src/java/src/util/BookingService.java:20` (`String.format("B%04d", storage.getBookings().size() + 1)`) и `src/java/src/util/SessionService.java:24` (`String.format("S%04d", storage.getSessions().size() + 1)`)
- **Место в коде:** обе строки форматируют ID из размера соответствующего списка + 1.
- **В чём проблема.** Во-первых, это дублирование кода - один и тот же шаблон `%04d` написан дважды. Во-вторых, подход `size() + 1` ломается при удалении записи: если удалить бронь из списка, следующая получит уже занятый ID (коллизия). Пусть сейчас удаления и нет, но это хрупкий инвариант. В-третьих, если одновременно создать бронь в двух потоках, тоже возможна коллизия.
- **Что предлагаю.** Вынести генерацию ID в общий метод `IdGenerator.next(prefix)` (или в `InMemoryStorage` - `nextBookingId()`, `nextSessionId()`), а счётчик хранить отдельно от размера списка - например, простым `AtomicInteger` в `InMemoryStorage`. Это уберёт дублирование и сделает ID устойчивыми к удалениям.
